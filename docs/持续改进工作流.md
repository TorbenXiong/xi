# 持续改进工作流

这份文档把 `yetone/magpie` 的研发实践转译成适合 xi 的工作流程。目标是让每轮变更都留下可复用的证据和经验，逐步减少返工；它不是让 Agent 获得无限修改、自动合并或自动发布的权限。

## 研究边界

你提供的 [ChatGPT 讨论](https://chatgpt.com/share/6ae8495c-8560-83e9-8835-044d72cbb491) 很有启发，但其中关于 `Specs → Plan → Build → Validate → Review`、`IMPLEMENTATION_PLAN.md` 和 `SKILL.md` 的具体例子实际指向 [apache/magpie](https://github.com/apache/magpie)，不是本次目标的 [yetone/magpie](https://github.com/yetone/magpie)。因此这些内容作为方法假设使用，关于 yetone 项目的事实以其仓库和 Actions 为准。

## Magpie 真正可复用的机制

### 1. 把项目状态放到短而稳定的外部规则里

yetone/magpie 的根目录 `AGENTS.md` 要求改代码前阅读子系统设计、代码标准、贡献者规则和 `LESSONS.md`；`CLAUDE.md` 只负责引入这些规则。Agent 每轮从文件重建上下文，规则不会依赖一段不断变长的对话。

### 2. 把任务限制在一个可审查的目标

代码标准要求变更只做目标所需的事情，修复要覆盖完整路径和所有兄弟场景。任务越小，失败原因越容易定位，审查也能针对用户结果而不是“改了很多文件”做判断。

### 3. 让验证先于承诺

其标准要求修复附带一个在旧代码上会失败的测试、使用真实输入、禁止测试访问真实网络，并要求记录完整套件和未运行的检查。测试失败不会被当作“main 本来就红”而跳过；要么修复根因，要么单独记录和处理。

### 4. 把返工转成规则

`LESSONS.md` 明确写出：代码由 Agent 编写、审查、合并和发布；每天复盘当天的返工、错误合并和薄弱验证。每条经验写成规则、原因和证据，连续三个独立周期出现后才升级为长期代码标准。这是持续改进的核心，不是单纯增加测试数量。

### 5. 让风险在合并前暴露

贡献者审查先检查越过目标范围的网络、凭据、依赖、发布脚本和配置变更，再决定是否运行代码。不可逆操作要有真实环境或沙盒验证；发布工作流只有在对应测试完成后才继续。当前 Actions 页面能看到 Test 与 Release 按 commit 运转，且测试工作流会串行等待机器资源。

## 对 xi 的评估

xi 已有跨层 AppServer、桌面端、CLI、SQLite、离线测试和审查记录，适合采用“任务小、证据全、经验可升级”的闭环。当前缺口是：项目规则没有集中定义，经验没有独立入口，任务缺少统一验收卡，复盘结果也没有升级门槛。

不直接复制 Magpie 的高频发布、代理自动合并或多会话并发。xi 目前规模更小、还有未完成的跨平台和 Runtime 能力，且外层规则要求用户单独确认每次提交；这里保留人工决定范围、commit、push、合并和发布。速度指标也不采用 commit 数，而看一次通过率、返工次数、未验证承诺和用户复现是否关闭。

## xi 的一轮迭代

```text
任务卡/用户报告
      ↓
复现与基线（确认当前行为和证据缺口）
      ↓
一个目标的实现（独立分支或 worktree）
      ↓
定向验证 + 兄弟场景检查 + 跨层验收
      ↓
审查变更范围、风险和验证记录
      ↓
用户决定提交/合并/发布
      ↓
复盘返工与漏测，更新 LESSONS.md
      ↓
下轮从任务卡、规则文件和当前代码重新开始
```

每个阶段的出口条件如下：

| 阶段 | 必须留下的证据 | 不满足时的处理 |
| --- | --- | --- |
| 任务卡 | 触发、用户结果、范围、验收、风险 | 不开始大范围实现，先补充目标 |
| 基线 | 原始复现、当前测试或明确的未知项 | 未复现就标记假设，不声称已定位 |
| 实现 | 一个目标、影响调用链、兄弟入口清单 | 发现第二个目标就拆任务 |
| 验证 | 新测试/验收结果、运行命令、未运行项 | 红测修根因或单独登记，不绕过 |
| 审查 | diff 范围、敏感操作、兼容性、文档同步 | 证据不足则退回实现阶段 |
| 落地 | 审查过的 commit 和完整验证记录 | 不自动提交、推送或发布 |
| 复盘 | 规则、原因、证据、seen 次数、防再犯检查 | 只记录可执行经验，不写流水账 |

## 运行节奏

- **每次任务结束**：更新任务卡的验证记录；若出现返工、漏测、错误假设或有效的边界发现，立即追加 `LESSONS.md`。
- **每周一次**：检查本周红测、重复问题、未关闭用户报告和未验证承诺；为重复规则增加测试或审查问题。
- **每三次独立复盘**：把反复出现的规则从经验库升级到 `AGENTS.md`、测试门槛或稳定工具检查，并在经验条目保留升级证据。
- **发布前**：只基于已经验证的审查头发布；未运行的检查、真实环境未试的行为和已知红测都必须显式列出，由维护者决定是否延期。

## 成功标准

持续改进不是“让 Agent 修改更多代码”，而是让后续迭代更少重复犯同一类错误。建议观察四个指标：一次通过率、同一问题的返工轮数、验证记录完整率、用户报告从复现到确认关闭的时间。它们用于发现流程瓶颈，不用于驱动无意义的高频提交。

本仓库已经落地的入口是：项目规则见 [`AGENTS.md`](../AGENTS.md)，经验库见 [`LESSONS.md`](../LESSONS.md)，任务卡见 [`迭代任务模板`](迭代任务模板.md)。
