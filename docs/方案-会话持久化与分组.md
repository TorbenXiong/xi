# 会话持久化与分组方案

状态：阶段 A-D 已实现，阶段 E（上下文裁剪与检索增强）待实现  
适用版本：`xi-agent-cli` 当前 CLI 基线  
目标：在保留现有流式模型调用的基础上，支持会话持久化、分组管理、失败恢复和后续客户端复用。

## 1. 当前基线与问题

当前程序在 `main` 中使用内存 `Vec<Message>` 保存消息。每轮请求把完整消息历史发送给模型，程序退出后历史丢失，也没有会话切换、删除、搜索和分组能力。

当前流式输出已经具备以下行为：

- 请求使用 `stream: true`。
- 复用一个 `reqwest::Client`。
- 按 SSE 增量内容输出。
- 普通 JSON 响应可以回退处理。

持久化方案不应破坏这些行为。数据库负责保存会话状态和最终消息，不能在每个 token 到达时写数据库，否则磁盘 I/O 会抵消流式输出的收益。

## 2. 范围

### 2.1 第一阶段包含

- 本地 SQLite 数据库。
- 会话创建、恢复、切换、重命名、删除和清空。
- 分组创建、列出、重命名、切换、归档和删除。
- 会话在分组之间移动。
- 流式回复完成、失败和中断状态保存。
- 程序重启后恢复最近使用的分组和会话。
- 基础搜索和导出接口预留。

### 2.2 第一阶段不包含

- 多用户同步。
- PostgreSQL 远程部署。
- 跨分组标签系统。
- 分组共享和权限控制。
- 数据库加密。
- 自动摘要和复杂上下文压缩的完整实现。

这些功能可以建立在本方案的数据模型上，但不应阻塞本地单用户版本。

## 3. 核心决策

### 3.1 存储选择

使用 SQLite。理由：

- 当前产品以本地 Runtime 和 CLI 为主。
- 会话、消息和分组需要事务、索引和条件查询。
- 不需要额外数据库服务。
- 后续可将仓储层替换为 PostgreSQL，而不让业务层直接依赖 SQL 细节。

建议依赖：

- `rusqlite`：SQLite 访问和事务。
- `uuid` 或等价 ID 生成方案：为会话、消息和运行记录生成稳定 ID。

这两项属于依赖变更，实际实现前需要单独确认版本、来源和锁文件变化；本方案文档不执行安装或解析依赖。

### 3.2 分组语义

第一版使用扁平分组：一个会话只能属于一个分组。

- 内置“未分组”分组，不能删除。
- 新建会话默认放入当前分组。
- 删除普通分组时，将其会话移动到“未分组”，不级联删除会话。
- 分组归档后默认不显示，但会话和消息保留。
- 第一版不实现嵌套分组和标签。

扁平分组可以覆盖“项目”“任务”“主题”等主要场景，同时避免第一版引入树形移动、循环引用和复杂 UI。未来如果确认需要层级分组，可以通过迁移增加 `parent_id`，不改变会话和消息表。

### 3.3 标识符

业务对象使用应用生成的稳定字符串 ID，推荐 UUID。数据库主键不依赖自增值，便于未来导出、同步和迁移到 PostgreSQL。

### 3.4 删除语义

默认采用软删除或归档：

- 分组删除：会话移入“未分组”，分组记录保留归档时间。
- 会话删除：设置 `archived_at`，默认列表不显示。
- 永久删除：作为显式的后续命令，要求用户确认，并在事务中删除消息、运行记录和会话。

这样可以避免误操作直接破坏用户历史。

## 4. 数据模型

### 4.1 `conversation_groups`

```sql
CREATE TABLE conversation_groups (
    id           TEXT PRIMARY KEY,
    name         TEXT NOT NULL,
    sort_order   INTEGER NOT NULL DEFAULT 0,
    is_system    INTEGER NOT NULL DEFAULT 0,
    created_at   TEXT NOT NULL,
    updated_at   TEXT NOT NULL,
    archived_at  TEXT
);

CREATE UNIQUE INDEX idx_groups_active_name
ON conversation_groups(name COLLATE NOCASE)
WHERE archived_at IS NULL;
```

字段约束：

- `name` 去除首尾空白后不能为空。
- `is_system = 1` 的“未分组”不能重命名和删除。
- 活跃分组名称不区分大小写唯一。
- `sort_order` 用于用户自定义排序，不依赖创建时间。

### 4.2 `conversations`

```sql
CREATE TABLE conversations (
    id           TEXT PRIMARY KEY,
    group_id     TEXT NOT NULL,
    title        TEXT NOT NULL,
    model        TEXT NOT NULL,
    created_at   TEXT NOT NULL,
    updated_at   TEXT NOT NULL,
    archived_at  TEXT,
    FOREIGN KEY (group_id) REFERENCES conversation_groups(id)
);

CREATE INDEX idx_conversations_group_updated
ON conversations(group_id, archived_at, updated_at DESC);
```

约束和行为：

- `group_id` 必须指向有效分组。
- `title` 可以由第一条用户消息自动生成，也可以手动修改。
- `updated_at` 在新消息、重命名、移动和恢复时更新。
- 列表默认过滤 `archived_at IS NOT NULL`。

### 4.3 `messages`

```sql
CREATE TABLE messages (
    id              TEXT PRIMARY KEY,
    conversation_id TEXT NOT NULL,
    sequence        INTEGER NOT NULL,
    role            TEXT NOT NULL CHECK (role IN ('system', 'user', 'assistant', 'tool')),
    content         TEXT NOT NULL,
    status          TEXT NOT NULL CHECK (
        status IN ('pending', 'streaming', 'complete', 'failed', 'interrupted')
    ),
    error           TEXT,
    created_at      TEXT NOT NULL,
    completed_at    TEXT,
    FOREIGN KEY (conversation_id) REFERENCES conversations(id) ON DELETE CASCADE,
    UNIQUE (conversation_id, sequence)
);

CREATE INDEX idx_messages_conversation_sequence
ON messages(conversation_id, sequence);
```

只有 `complete` 消息进入默认模型上下文。`failed` 和 `interrupted` 消息保留给用户查看，但不能误发给模型。

### 4.4 `runs`

`runs` 用于记录一次模型请求，而不是把请求状态混在会话状态中。

```sql
CREATE TABLE runs (
    id              TEXT PRIMARY KEY,
    conversation_id TEXT NOT NULL,
    user_message_id TEXT NOT NULL,
    assistant_id    TEXT,
    model           TEXT NOT NULL,
    status          TEXT NOT NULL CHECK (
        status IN ('queued', 'running', 'completed', 'failed', 'interrupted')
    ),
    started_at      TEXT NOT NULL,
    finished_at     TEXT,
    error           TEXT,
    usage_json      TEXT,
    FOREIGN KEY (conversation_id) REFERENCES conversations(id) ON DELETE CASCADE,
    FOREIGN KEY (user_message_id) REFERENCES messages(id),
    FOREIGN KEY (assistant_id) REFERENCES messages(id)
);

CREATE INDEX idx_runs_conversation_started
ON runs(conversation_id, started_at DESC);
```

`runs` 为后续耗时统计、重试、取消和审计提供边界。第一版可以只保存模型返回的 usage 信息，供应商没有返回时保持为空。

## 5. 消息写入和流式请求流程

### 5.1 成功流程

```text
用户输入
  → 事务 A：写入 user 消息，创建 run(status=queued)
  → 提交事务 A
  → 创建 assistant 占位消息(status=streaming)
  → run 更新为 running
  → 调用模型并持续输出增量内容
  → 内存中累积 assistant 完整文本
  → 事务 B：写入 assistant 内容，更新为 complete
  → run 更新为 completed
```

assistant 占位消息可以与 `run` 的 `running` 状态放在同一个事务中，推荐这样做，避免出现运行记录存在但没有对应 assistant 记录的情况。

### 5.2 失败和中断流程

- HTTP 错误：assistant 更新为 `failed`，`error` 保存经过截断的错误信息，run 更新为 `failed`。
- 网络中断：如果已经收到部分文本，将部分文本保存为 `interrupted`；如果没有文本，内容为空。
- 用户取消：assistant 和 run 更新为 `interrupted`。
- 程序崩溃：下次启动时，将上次遗留的 `running`、`streaming` 记录标记为 `interrupted`。

流式期间不按 token 写数据库。正常完成只写一次；异常退出时最多再写一次部分结果。

### 5.3 重试流程

重试不覆盖原失败记录，而是创建新的 run 和 assistant 消息。这样能够保留故障历史，也便于比较不同模型或参数的结果。

## 6. 上下文构建

持久化历史与发送给模型的上下文必须分离。

```text
数据库完整历史
  → 过滤 archived / failed / interrupted
  → 应用 system prompt
  → 按 token 预算保留最近消息
  → 加入摘要（如果存在）
  → 生成 ChatRequest.messages
```

第一版先实现：

- 只读取当前会话。
- 只发送 `complete` 消息。
- 保留全部历史，但增加明确的上下文构建接口。

第二版再实现：

- 最大输入 token 预算。
- 早期消息摘要。
- 按分组配置 system prompt 和默认模型。
- 记录摘要对应的消息范围，避免重复摘要。

这部分会直接影响调用速度，不能把“数据库保存成功”误认为“模型上下文已经优化”。

## 7. CLI 管理命令

### 7.1 分组命令

```text
/groups                         列出活跃分组、会话数量和最近更新时间
/group-new <name>               新建分组并切换到该分组
/group-use <id-or-name>         切换当前分组
/group-rename <name>            重命名当前分组
/group-move <conversation> <group>  移动会话
/group-archive <id-or-name>     归档分组
/group-delete <id-or-name>      删除分组，会话转入“未分组”
```

### 7.2 会话命令

```text
/new [title]                    在当前分组创建并切换到新会话
/sessions                       列出当前分组会话
/sessions --all                 列出所有分组会话
/use <id-or-title>              切换会话
/rename <title>                 重命名当前会话
/clear                          清空当前会话消息
/archive                        归档当前会话
/delete                         归档当前会话
/search <keyword>              搜索会话标题和消息
/export <path>                 导出当前会话
```

命令解析应独立于模型调用，避免把 CLI 分支继续堆积在 `main` 的请求循环中。

## 8. Rust 模块边界

建议将当前单文件实现逐步拆分为：

```text
src/
├── main.rs                 启动、输入循环和退出处理
├── config.rs               配置加载
├── domain.rs               Group、Conversation、Message、Run
├── storage/
│   ├── mod.rs              仓储 trait 和错误类型
│   ├── sqlite.rs           SQLite 连接、迁移和 SQL
│   └── migrations/         版本化迁移脚本
├── conversation.rs         会话和分组业务规则
├── context.rs              模型上下文构建和 token 预算
└── model.rs                Provider 请求、SSE 和响应解析
```

第一版不要求一次性完成全部拆分。最小可接受边界是先把 SQLite 访问隔离到 `storage`，不要让 `main` 直接编写 SQL。

仓储层至少需要这些操作：

```text
list_groups()
create_group(name)
rename_group(id, name)
archive_group(id)
delete_group(id)

create_conversation(group_id, title, model)
list_conversations(group_id)
load_conversation(id)
move_conversation(id, group_id)
rename_conversation(id, title)
archive_conversation(id)

append_user_message(...)
start_run(...)
complete_assistant_message(...)
fail_run(...)
interrupt_run(...)
```

业务层负责权限、默认分组、删除语义和状态转换；仓储层负责 SQL、事务和迁移。

## 9. 数据库初始化和迁移

数据库文件不放入仓库。默认路径：

```text
Windows: %LOCALAPPDATA%\\xi\\xi.db
macOS:   ~/Library/Application Support/xi/xi.db
Linux:   ~/.local/share/xi/xi.db
```

初始化步骤：

1. 创建父目录。
2. 打开 SQLite 连接。
3. 开启 `foreign_keys`。
4. 设置 `journal_mode=WAL`。
5. 执行未应用的迁移。
6. 创建或恢复系统“未分组”。
7. 恢复上次活跃分组和会话。

迁移通过 `PRAGMA user_version` 或独立 migration 表管理。每个迁移必须可重复检查，失败时回滚当前事务。

当前项目没有旧数据库，因此首个迁移只负责创建表和默认分组；后续结构调整必须增加新迁移，不直接修改旧迁移文件。

## 10. 索引、性能和并发

- 分组列表按 `sort_order`、`updated_at` 查询。
- 会话列表按 `group_id + updated_at` 查询。
- 消息按 `conversation_id + sequence` 查询。
- 搜索功能初期使用标题和消息的普通查询；数据量增大后再评估 SQLite FTS5。
- 每次用户输入和 assistant 完成使用短事务。
- 不在流式 token 循环内写数据库。
- CLI 第一版只允许一个活动模型请求，避免同一会话并发写入。
- 未来支持并发任务时，必须通过 run 和 sequence 约束区分不同请求。

## 11. 测试计划

### 11.1 仓储测试

- 首次打开自动创建表和“未分组”。
- 重复初始化不会重复创建系统分组。
- 活跃分组名称不区分大小写唯一。
- 新建会话默认关联当前分组。
- 会话移动后列表归属正确。
- 删除分组后会话进入“未分组”。
- 删除“未分组”会返回业务错误。
- 消息 sequence 连续且按顺序恢复。
- 外键和级联删除行为正确。

### 11.2 运行状态测试

- 成功流式回复最终保存为 `complete`。
- HTTP 错误保存为 `failed`。
- 网络中断保存为 `interrupted`。
- 重启时遗留的 `running` 和 `streaming` 被标记为 `interrupted`。
- 失败重试不会覆盖原记录。

### 11.3 CLI 测试

- 分组创建、切换、重命名、移动和删除。
- 会话切换后只发送当前会话上下文。
- `/exit` 后重新启动可以恢复会话。
- 空输入、未知命令和不存在的 ID 返回可读错误。

### 11.4 验收场景

```text
启动 → 创建“项目 A”分组 → 新建会话 → 对话两轮
退出 → 重启 → 自动恢复同一会话
创建“项目 B”分组 → 移动会话 → 在两个分组间切换
删除“项目 B” → 会话出现在“未分组”
模拟模型失败 → 失败状态和错误可见 → 重试产生新 run
```

## 12. 分阶段实施和审查点

### 阶段 A：领域模型和迁移

交付：表结构、迁移、默认分组、数据库路径和连接初始化。  
审查重点：字段、约束、删除语义、依赖变更。

### 阶段 B：仓储层

交付：分组、会话、消息和 run 的仓储操作及单元测试。  
审查重点：事务边界、错误处理、SQL 是否泄漏到业务层。

### 阶段 C：CLI 会话管理

交付：启动恢复、分组命令、会话命令和状态显示。  
审查重点：命令语义、默认分组、归档和恢复行为。

### 阶段 D：模型调用接入

交付：流式请求与 run/message 状态关联，成功、失败和中断落库。  
审查重点：是否按 token 写库、异常是否留下错误的 complete 消息、上下文是否只读取有效消息。

### 阶段 E：上下文与检索

交付：输入 token 预算、摘要接口、搜索和导出。  
审查重点：持久化历史与模型上下文是否分离，长会话性能是否可控。

## 13. 待评审决策

本方案默认采用以下选择：

1. 第一版使用扁平分组，不实现嵌套分组。
2. 一个会话只能属于一个分组，不实现标签。
3. 删除分组时会话移动到“未分组”。
4. 会话和消息默认软删除，永久删除后置。
5. 使用 SQLite 本地文件，不引入远程同步。
6. 流式期间只在内存累积，完成或异常时写一次数据库。
7. 使用稳定字符串 ID，推荐 UUID。

阶段 A-D 已按上述边界实现并通过本地测试；阶段 E 仍需要在真实长会话数据和模型 token 统计基础上单独设计。后续改动应继续按阶段拆分和审查，不一次性混入所有功能。
