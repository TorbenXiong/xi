# 会话持久化与分组方案

当前已实现关系化 SQLite、分组/会话管理、运行状态、流式 CLI，以及共用 AppServer 的桌面客户端。本文件保留设计决策和后续边界；代码讲解和接口细节分别见 [03 会话持久化与分组](learning/03-会话持久化与分组.md)、[04 应用端架构与调试](learning/04-应用端架构与调试.md)和 [应用 API](app-api.md)，避免重复维护 SQL 与命令清单。

## 已确定的行为

- 使用扁平分组；一个会话属于一个分组，暂不实现嵌套或标签。
- “未分组”由系统维护，不能重命名、归档或删除。
- 删除普通分组时先把会话移到“未分组”，再隐藏原分组，历史保留。
- 归档会话只隐藏数据；桌面端永久删除会话需要确认，事务中同时删除运行记录和消息。
- 新会话先是客户端草稿，发送首条消息后才保存；直接调用创建会话 API 则立即创建。
- 会话和运行分开：会话组织历史，run 记录每一轮的模型、状态、时间和错误。
- 用户消息、assistant 占位消息与 run 在一个事务中创建，成功后才发网络请求。
- 只有 `complete` 消息进入默认模型上下文。失败或中断的回复保留供查看和导出。
- CLI 输出 SSE 增量；不支持 SSE 的服务可以回退到普通 JSON。缺少结束事件的流不能伪装成完整成功。

## 存储和迁移

沿用主线的 `conversation_groups`、`conversations`、`messages`、`runs` 和 `app_state`，并增加 `providers`、`provider_models`。Provider 密钥在页面维护，不依赖配置文件。所有 UI 与 CLI 共用同一业务入口，不再各自维护工作区存储。

数据库默认位于平台用户数据目录的 `xi/xi.db`；`XI_DATA_DIR` 指向隔离测试目录。SQLite 开启外键、WAL 和忙等待。schema 版本 2 保留主线关系表，增加 Provider 存储和旧客户端快照导入。

旧 `config/xi.sqlite3` 以只读事务读取，目标导入整体提交并记录来源。原文件保留；重复启动不重复导入，失败不留下部分数据，既有主线历史不被覆盖。迁移测试使用假数据，不读取真实凭据。

同一个数据库只允许一个 Runtime 进程。多个 UI 应连接同一服务；实例锁防止第二个进程启动时误恢复仍在执行的 run。退出后锁文件保留不代表进程仍占用，操作系统文件锁才是判断依据。

## 性能与并发

- 分组、会话和消息使用已有索引查询，搜索目前使用标题/内容的普通 SQL 查询。
- 事务保持短小，不跨越模型网络调用。
- 流式首块立即保存，后续按 250 ms 或 8 KiB 增量节流；完成、失败或中断时保存完整结果。
- AppServer 当前串行协调聊天、清空、删除、移动和归档，避免迟到回复破坏历史。
- 长会话目前仍发送全部有效历史。FTS5、并发调度或后台任务应由实际数据量和性能验证驱动。

## 后续工作

上下文治理与检索仍需单独设计：

1. 在数据库完整历史与模型上下文之间增加 token 预算和构建层。
2. 先按状态和归档范围过滤，再选择摘要、近期消息或检索结果。
3. 摘要不能覆盖原始历史，搜索和导出继续使用完整记录。
4. 用真实长会话测量效果和成本，再决定是否引入 FTS5 或其他检索方案。

客户端事件订阅、Turn 调度、取消、取消归档界面、正式 Runtime sidecar 分发和远程多用户同步尚未实现。未来协议演进应继续遵守 UI、传输、业务、模型与存储之间的边界。

## 验证重点

- 重复初始化、默认分组保护、大小写唯一名称、消息顺序和外键约束。
- 跨分组移动、分组删除后保留历史、归档后的列表与搜索范围。
- 成功、失败、中断、遗留请求恢复及部分文本保存。
- 两个客户端的显式目标隔离，两个 Runtime 的同库互斥。
- 旧快照导入幂等性、原文件不变、无效消息时整体回滚。
- 实际 Runtime 与 CLI 的进程测试，包括流式输出、搜索、Markdown 导出和重启恢复。
