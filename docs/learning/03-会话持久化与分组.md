# 第三步：会话持久化、分组和运行状态

这一阶段解决的问题是：对话不能只存在进程内存中。程序退出后，用户应该能够重新打开原来的分组和会话，继续查看消息、切换会话和管理历史。

本阶段的完整链路是：

~~~text
启动 CLI
  → 打开本地 SQLite
  → 执行数据库迁移
  → 创建或恢复“未分组”
  → 恢复上次使用的分组和会话
  → 读取用户输入
  → 处理 / 命令，或创建一次模型 run
  → 保存 user 消息和 assistant 占位消息
  → 调用模型并流式输出
  → 根据结果保存 complete、failed 或 interrupted 状态
~~~

## 1. 三个核心概念

### 1.1 分组

分组用于组织会话，例如“项目 A”“学习”“临时咨询”。第一版是扁平分组：

- 一个会话只能属于一个分组。
- 系统会自动创建一个不能删除的“未分组”。
- 删除普通分组时，其中的会话移动到“未分组”。
- 分组归档后默认不显示，但数据库记录仍保留。

分组不是会话标题的一部分，而是独立的数据对象。这样后续桌面端可以显示分组、统计会话数量，也可以单独搜索和归档。

### 1.2 会话

会话是用户看到的一段连续对话，包含标题、所属分组、使用的模型和更新时间。会话本身不直接保存完整文本，消息存放在 messages 表中。

### 1.3 Run

一次用户输入到模型回复完成的过程称为一次 run。run 用来记录请求状态：

~~~text
queued → running → completed
                  ↘ failed
                  ↘ interrupted
~~~

会话负责“我有哪些历史”，run 负责“这一轮请求发生了什么”。分开后，失败重试不会覆盖原记录，也能统计耗时和错误。

## 2. 阅读入口

建议按以下顺序阅读：

1. src/main.rs：启动、输入循环和命令分派。
2. src/storage.rs：SQLite 连接、迁移、查询和事务。
3. main 中的 start_run、complete_run 和错误分支：理解一次消息如何落库。
4. call_model 和 SSE 解析：理解网络流和数据库状态如何衔接。
5. 本文末尾的测试：用最小场景验证数据模型。

当前版本把 CLI 编排放在 main.rs，把 SQL 和事务集中在 storage.rs。后续 Runtime 变复杂时，可以再拆成 domain、storage、conversation 和 model 模块。

## 3. 依赖和数据库位置

Cargo.toml 增加了两个依赖：

~~~toml
rusqlite = { version = "0.40.2", default-features = false, features = ["bundled"] }
uuid = { version = "1.26.1", features = ["v4"] }
~~~

- rusqlite 负责 SQLite 连接、参数绑定、事务和查询。
- bundled 让项目使用随依赖编译的 SQLite，减少目标机器缺少系统 SQLite 的问题。
- uuid 生成分组、会话、消息和 run 的稳定字符串 ID。

数据库不放在仓库中。Windows 默认位置是：

~~~text
%LOCALAPPDATA%\xi\xi.db
~~~

macOS 和 Linux 的默认位置分别是：

~~~text
~/Library/Application Support/xi/xi.db
~/.local/share/xi/xi.db
~~~

数据库包含用户对话内容，不能提交到 Git。config/local.toml 中的 API Key 也不能提交。

## 4. 数据库初始化

打开数据库的入口是 Store::open。它完成四件事：

1. 创建数据库父目录。
2. 打开 SQLite 文件。
3. 开启外键、WAL 和忙等待。
4. 执行迁移并确保系统分组存在。

~~~rust
let connection = Connection::open(path)?;
connection.pragma_update(None, "foreign_keys", true)?;
connection.execute_batch(
    "PRAGMA journal_mode = WAL; PRAGMA busy_timeout = 5000;"
)?;
~~~

### 4.1 为什么开启外键

会话依赖分组，消息和 run 依赖会话。外键可以阻止悬空数据，例如消息指向一个不存在的会话。

messages.conversation_id 使用 ON DELETE CASCADE，因此未来执行永久删除会话时，消息可以一起删除。当前 CLI 的 /delete 是归档，不会立即触发永久删除。

### 4.2 为什么使用 WAL

WAL（Write-Ahead Logging）适合本地读多写少的 SQLite 应用，可以减少读写互相阻塞。当前 CLI 一次只处理一个模型请求，因此不需要复杂的并发写入队列。

### 4.3 迁移版本

SQLite 的 PRAGMA user_version 保存当前结构版本。第一次打开时创建所有表并设置为版本 1：

~~~text
user_version = 0
  → 创建表、索引和 app_state
  → user_version = 1
~~~

后续不能直接修改已经执行过的 SQL。结构变化应该增加版本 2、版本 3 的迁移。

## 5. 五张表

### 5.1 conversation_groups

~~~text
id              分组 ID
name            分组名称
sort_order      排序值
is_system       是否系统分组
created_at      创建时间
updated_at      更新时间
archived_at     归档时间，可为空
~~~

活跃分组名称使用不区分大小写的唯一索引，避免同时出现 Project 和 project。

### 5.2 conversations

~~~text
id              会话 ID
group_id        所属分组
title           会话标题
model           创建时使用的模型
created_at      创建时间
updated_at      最近更新时间
archived_at     归档时间
~~~

updated_at 用于把最近活动的会话排在前面，也用于恢复最近使用的会话。

### 5.3 messages

~~~text
id              消息 ID
conversation_id 所属会话
sequence        会话内顺序
role            system/user/assistant/tool
content         消息内容
status          pending/streaming/complete/failed/interrupted
error           错误信息，可为空
created_at      创建时间
completed_at    完成时间，可为空
~~~

sequence 是会话内唯一递增序号。模型上下文只读取 status = complete 的消息，因此失败或中断的 assistant 内容不会被误发给模型。

### 5.4 runs

~~~text
id              run ID
conversation_id 所属会话
user_message_id 本次用户消息
assistant_id    对应 assistant 消息
model           本次调用的模型
status          queued/running/completed/failed/interrupted
started_at      开始时间
finished_at     完成时间
error           错误信息
usage_json      供应商返回的 token 使用量，当前可为空
~~~

注意：消息状态使用 complete，而 run 状态使用 completed。这是有意区分的：消息描述内容是否完整，run 描述一次操作是否完成。

### 5.5 app_state

保存 CLI 的轻量状态：

~~~text
active_group_id
active_conversation_id
~~~

它不是业务历史，只用于下一次启动时恢复用户上次所在的位置。

## 6. 启动恢复逻辑

main 启动后依次执行：

~~~rust
let mut store = Store::open(&database_path)?;
store.mark_stale_runs_interrupted()?;

let mut active_group = restore_group(&store)?;
let mut active_conversation =
    restore_conversation(&store, &active_group.id, &config.model)?;
~~~

恢复规则如下：

1. 如果 app_state.active_group_id 仍指向活跃分组，就恢复它。
2. 否则恢复“未分组”。
3. 如果上次会话仍属于当前分组，就恢复它。
4. 否则选择当前分组最近更新的会话。
5. 如果分组没有会话，创建一个“新会话”。

启动时还会把上次遗留的 running、queued、streaming 和 pending 标记为 interrupted。进程崩溃后无法继续原来的 HTTP 连接，不能把这些记录伪装成成功。

## 7. 一次成功对话的完整流程

用户输入普通文本时，主循环执行以下步骤：

~~~text
用户输入
  → Store::start_run
  → 事务写入 user 消息
  → 事务写入 assistant 占位消息
  → 事务写入 running run
  → 读取 complete 消息
  → 调用模型
  → 流式打印增量
  → Store::complete_run
~~~

### 7.1 为什么要创建 assistant 占位消息

在模型还没有返回内容时，数据库已经知道存在一次未完成的 assistant 回复。如果进程此时退出，下一次启动可以找到这条 streaming 消息并标记为 interrupted。

这三个对象在一个事务中写入：

~~~text
user message:      complete
assistant message: streaming
run:               running
~~~

事务成功提交后，才开始网络请求。这样不会出现用户输入已写入但 run 不存在的半成品状态。

### 7.2 为什么只读取 complete 消息

调用模型前执行 load_messages(conversation_id, true)。第二个参数为 true 时，SQL 增加 status = complete：

- 当前 user 消息会发送给模型；
- 之前成功的 assistant 消息会发送给模型；
- 失败或中断的 assistant 内容不会污染下一轮上下文；
- assistant 占位消息不会被发送。

## 8. 流式输出和持久化的边界

流式输出的职责是让用户尽早看到内容，数据库的职责是保存可靠的最终状态。当前实现不会每收到一个 token 就写 SQLite，而是在内存中累积完整回复：

~~~text
SSE chunk
  → 解析 data:
  → 提取 delta.content
  → print + flush
  → answer.push_str(...)
~~~

流结束后执行 Store::complete_run。这能避免高频磁盘写入，也减少数据库锁竞争。

### 8.1 普通 JSON 回退

如果服务端没有返回 text/event-stream，程序会读取普通 JSON，并提取 choices[0].message.content。这样某些 OpenAI-compatible 服务即使不支持流式，也能继续工作。

### 8.2 中途失败

ModelError 除了错误文本，还携带已经收到的部分内容：

~~~text
无部分内容 → assistant = failed，run = failed
有部分内容 → assistant = interrupted，run = interrupted
~~~

这样终端上已经显示的内容不会从数据库中消失。程序重启后，用户可以通过 /export 查看这部分内容。

## 9. 命令处理

命令在发起模型请求之前判断。handle_command 返回：

~~~text
Ok(true)  退出程序
Ok(false) 命令已处理，继续循环
Err       打印命令错误，继续循环
~~~

### 9.1 分组命令

~~~text
/groups
/group-new <名称>
/group-use <ID或名称>
/group-rename <名称>
/group-move <会话> <分组>
/group-archive [分组]
/group-delete [分组]
~~~

/group-delete 和 /group-archive 当前都采用安全的归档语义。删除普通分组时，会话先转移到“未分组”；系统分组不能重命名、归档或删除。

### 9.2 会话命令

~~~text
/new [标题]
/sessions
/sessions --all
/use <ID或标题>
/rename <标题>
/clear
/archive
/search <关键词>
/export <路径>
~~~

/clear 会在一个事务中删除当前会话的消息和 run，但保留会话本身。/archive 只隐藏会话，不立即删除数据。

### 9.3 名称和 ID

分组可以用 ID 或名称切换，会话可以用 ID 或标题切换。名称比较不区分大小写。生产环境中更推荐使用 UUID，因为标题可能重复。

## 10. 手工练习

启动程序：

~~~powershell
cargo run
~~~

依次执行：

~~~text
/groups
/group-new 项目A
/new 登录问题
/sessions
/group-new 项目B
/new 数据库问题
/groups
/sessions --all
/use 登录问题
/group-move 登录问题 项目B
/group-use 项目B
/search 问题
/export conversation.md
/exit
~~~

再次启动后，检查当前分组和当前会话是否恢复。为了避免真实模型调用，管理命令可以在没有输入普通消息的情况下单独测试。

在 Windows PowerShell 中，如果中文显示为乱码而 ID 正常，通常是终端代码页问题，不代表 SQLite 内容损坏。文件和数据库内部使用 UTF-8。

## 11. 测试如何对应实现

当前共有五个单元测试：

- main.rs：LF 和 CRLF SSE 事件分隔符、增量内容和 [DONE] 事件。
- storage.rs：初始化系统分组、创建分组和会话、保存完整回复、删除分组后迁移会话、保存中断回复的部分内容和错误信息。

执行验证：

~~~powershell
cargo fmt
cargo check --offline
cargo test --offline
~~~

当前实现的测试使用 SQLite 内存数据库，不会修改用户的真实会话文件。

## 12. 还没有解决什么

持久化已经完成，但每次请求仍会把当前会话的全部 complete 消息发送给模型。长会话会带来更多输入 token、更高费用和更长的首 token 延迟。

下一阶段应该增加：

1. 输入 token 预算；
2. 最近消息优先策略；
3. 早期消息摘要；
4. 摘要覆盖范围记录；
5. 大量会话的 FTS5 搜索；
6. token 使用量和 TTFT/总耗时统计。

这部分不能通过单纯增加 SQLite 表解决，必须在数据库完整历史和本次发送给模型的上下文之间增加独立的上下文构建层。

## 13. 推荐学习顺序

1. 阅读 Store::open 和迁移 SQL，确认数据库如何创建。
2. 阅读 create_group、create_conversation 和 list_*，理解查询对象。
3. 阅读 start_run，确认三个对象为什么放在同一个事务。
4. 阅读 finish_run，确认 complete、failed 和 interrupted 的状态转换。
5. 阅读 main 的启动恢复和命令分派。
6. 阅读 call_model 的 SSE/JSON 双路径。
7. 运行五个单元测试和 CLI 管理命令练习。
8. 最后再审查长会话上下文裁剪方案。

建议每次只审查一个边界：数据库结构、业务状态、命令解析、模型调用和上下文构建不要混在同一次修改中。
