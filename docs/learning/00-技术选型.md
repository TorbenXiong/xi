# xi 技术选型

> 状态：第一版基线，2026-10-28
>
> 目标：构建一个通用 Agent Platform，支持本地执行、远程连接和多端访问。

本文是目标架构和选型基线，不代表全部能力已实现。当前采用 Tauri 2 + React、Rust Runtime、关系化 SQLite 和 HTTP JSON API；CLI 支持模型流式输出，JSON-RPC、客户端事件流、工具执行、MCP 与远程服务仍为规划。已落地内容见 [03-项目会话与持久化](03-项目会话与持久化.md)和 [04-应用端架构与调试](04-应用端架构与调试.md)。

## 1. 先统一一个产品前提

“支持各端使用”不等于每个端都运行完整 Agent。

- Windows、macOS、Linux：可以运行完整的本地 Agent，访问文件、进程、浏览器和开发工具。
- Web、Android、iOS：优先作为控制端，连接本地或远程 Agent Runtime，查看任务、审批权限和获取结果。
- 同一个 Agent Runtime 应能以本地进程或远程服务运行，客户端只是不同入口。

因此，第一原则是：**Agent Runtime 与客户端、模型供应商、执行环境解耦。**

## 2. 已确定的技术选型

| 层次 | 选择 | 说明 |
| --- | --- | --- |
| Agent Harness | **Rust** | 原生二进制、资源控制、系统调用、跨平台分发和长期运行能力。 |
| 异步运行时 | **Tokio** | Rust 生态成熟的异步运行时。 |
| Agent Loop | 自研最小循环 | 先掌握消息、上下文、工具调用、状态和事件，再评估高层 Agent Framework。 |
| 执行抽象 | `ExecutionBackend` | 统一抽象原生进程、OS Sandbox、容器、远程执行和浏览器等后端。 |
| 工具协议 | **MCP** | 对外接入工具、资源和提示，不重新发明通用工具协议。MCP 基于 JSON-RPC 2.0。 |
| IDE 协议 | **ACP（后续）** | 面向代码编辑器和编程 Agent 的互操作；不是第一阶段的核心依赖。 |
| 客户端通信 | JSON-RPC 2.0 | 本地客户端与 Runtime 之间使用双向请求、响应和通知。 |
| 远程通信 | HTTPS + WebSocket | 远程连接、实时事件和任务审批；协议层与传输层分离。 |
| 桌面端 | **Tauri 2 + React + TypeScript** | 桌面端优先，适合终端、代码编辑器、Diff、文件浏览器和实时任务界面。 |
| Web 端 | React + TypeScript | 复用协议、数据模型和 UI 逻辑，作为远程控制入口。 |
| 移动端 | 暂定 Tauri 2 或 Flutter | 先验证远程控制需求，再决定是否需要独立移动 UI 技术。 |
| 本地持久化 | **SQLite** | 保存配置、会话、任务、事件和工具审计；适合本地优先模式。 |
| 远程持久化 | PostgreSQL | 多用户和远程部署出现后再启用，不作为本地版本前置依赖。 |
| 日志追踪 | `tracing` + OpenTelemetry | 记录 Agent Loop、工具调用、权限决策和执行耗时。 |
| 插件执行 | MCP 优先，WASM 后评估 | 先解决生态接入，再验证 WASM 的隔离和权限模型。 |

Tauri 2 官方定位是使用 Web 前端构建桌面和移动应用，并提供 Rust、Swift、Kotlin 等原生绑定；因此它适合作为客户端外壳，但不能成为 Agent Harness 的依赖边界。[Tauri 官方文档](https://v2.tauri.app/start/)

MCP 的标准能力包括资源、提示和工具，并明确要求实现方处理用户同意、访问控制和工具安全。[MCP 规范](https://modelcontextprotocol.io/specification/2025-06-18)

ACP 专门解决代码编辑器与编程 Agent 的通信，第一阶段先保留接口，不提前实现完整 ACP 适配。[ACP 官方仓库](https://github.com/agentclientprotocol/agent-client-protocol)

## 3. 核心架构

```text
Client Layer
  Desktop / Web / Mobile / CLI
              │
       Agent Protocol
       JSON-RPC + Events
              │
      Agent Server / App Server
   Session · Auth · Events · Approval
              │
       Agent Harness（Rust）
   ┌──────────┼───────────┐
   │          │           │
Agent Engine  Model Engine Execution Engine
Agent Loop    Providers   Shell / Files / Browser
Context       Streaming   Native / Sandbox / Remote
Memory        Routing     Permissions / Cancellation
              │
        SQLite / PostgreSQL
```

最重要的边界是 `Agent Engine` 与 `Execution Engine` 分离。

例如，Agent Engine 只产生“执行 `npm test`”的意图；Execution Engine 决定工作目录、目标设备、权限范围、审批要求、超时、沙盒和进程树终止方式。这样同一个 Agent 才能在本地 Windows、Linux 容器或远程服务器中运行。

逻辑上的模块不等于部署上的微服务。第一版可以让 Agent Server、Harness 和 Execution Engine 在同一个 Rust 进程中运行，等远程、多用户或长任务出现后再拆分。

## 4. 暂不锁定的决策

- 桌面端是否长期使用 Tauri，或改为 Electron。
- 移动端使用 Tauri 2 还是 Flutter。
- 是否实现 WASM 插件系统。
- 是否引入分布式调度、独立 Sub-Agent 进程或长期记忆服务。
- 是否使用 LangChain、LangGraph 或其他 Agent Framework。
- 是否需要向量数据库。

这些问题应由运行能力原型和真实需求决定，而不是先凭偏好定死。

## 5. 实施顺序

### 阶段 1：独立 Runtime 和 CLI

先完成配置和模型 Provider 抽象、最小 Agent Loop、Shell/文件/计算器工具、上下文和会话管理、工具权限审批、超时、取消、审计事件、SQLite 持久化和最小 MCP Client。

CLI 是第一阶段的测试入口，也能避免 UI 掩盖 Runtime 的问题。

### 阶段 2：桌面客户端

使用 Tauri 2 + React 实现多会话、流式输出、工具执行展示、Diff、权限确认和模型配置。

### 阶段 3：远程 Runtime

实现 Runtime 的远程连接、身份认证、任务事件流、断线恢复和多设备访问。此时再引入 PostgreSQL。

### 阶段 4：Web 和移动客户端

基于既有协议实现远程任务管理、审批和结果查看；只有确认移动端需要本地能力时，才让移动端承载更多 Runtime 能力。

## 6. 首个可验证目标

- Rust CLI 能创建一次 Agent Run。
- Agent 能调用一个带 schema 的工具。
- 工具执行前触发权限决策，执行后记录事件和结果。
- 运行过程可通过 JSON-RPC 请求和事件通知观察。
- 关闭并重新启动后，SQLite 能恢复会话和运行记录。
- 后续 Tauri、Web、移动客户端都只依赖该协议，不直接依赖 Agent Loop。

## 7. 本次修正说明

之前文档提出的“Flutter + Python + FastAPI”更适合快速构建一个跨端聊天应用，但没有充分体现本项目的本地执行、沙盒、进程管理和通用 Runtime 目标。本版改为以 Rust Harness 为核心；Python、FastAPI、Flutter 仍可作为未来特定服务或客户端的备选，但不再作为当前主架构的前置决定。
